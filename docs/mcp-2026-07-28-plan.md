# MCP 2026-07-28: work plan

Brief for the agent that moves sitegeist to the MCP specification released on 2026-07-28. Written 2026-11-24 against commit `ce46a16`, from the code and from the pages listed under Sources. Facts marked "not confirmed" were not answered by those pages: re-check them before relying on them.

## Outcome (2026-11-24, SDK 2.4.0)

Items 0 to 7 are done on branch `feat/mcp-2026-07-28`. What was measured and decided:

- Harness eras, measured with a dual-era v2 probe server on MBProM3: Claude Code 2.1.331 negotiates 2026-07-28 and declares `elicitation: {form, url}`, also under `claude -p`, which cancels a form question at once. Codex 0.172.0 stays on 2025-06-18. omp is not installed on either Mac and was not tested. Items 1 and 2 are therefore not preparation only: Claude Code gets the 2026 path as soon as this ships.
- Bundling: `@modelcontextprotocol/client` resolves its `browser` condition to the `@cfworker/json-schema` validator, which generates no code. The connector client bundles with no ajv and no `new Function`, so the `noOutputValidation` override was removed and output schemas are validated. The ajv still in `sidepanel.js` comes from pi-ai's `validation.ts`.
- Instructions travel in the `server/discover` result; a client pinned to 2026-07-28 gets the same text and the same 38 tools (`scripts/e2e/mcp-eras.e2e.mjs`).
- Permission prompt: one path for both eras. The tool call returns `inputRequired`; on 2025-era connections the SDK's legacy shim sends it as `elicitation/create` and re-enters the handler. `requestState` (HMAC-sealed with a per-process key, 10 minutes) carries the extension's `requestId` and the id of the suspended tool call. The extension now sends `callId` with `permission_request`, so the question goes to the call that raised it. Code: `cli/src/permission-prompts.ts`.
- Between the two rounds the bridge request stays open in the extension, waiting on its decision. The extension's 90 s handler timeout (`HANDLER_TIMEOUT_MS`) ends the navigation if the answer is slower; an answer that arrives later still takes effect (`allow_host` is saved) and the retry returns the timed-out result. A suspended call that is never resumed is dropped 10 minutes after it ends.
- `versionNegotiation: 'auto'` on the native transport probes in place. The SDK tells stdio from HTTP by the `stderr` and `pid` fields, so `NativeConnectorTransport` declares both (as `null`): a silent legacy server then falls back to `initialize` on the same process. Spawns, counted in `connectors.e2e.mjs`: 2026 server 1, legacy server 1, a legacy server that exits on the probe 2 (one in-place probe, then a start with `prior: { kind: 'legacy' }`). The probe waits at most 3 s, inside the manager's 8 s connect budget.
- `input_required` from connectors: no elicitation capability is declared and `autoFulfill` is off. Such a call fails with an error that names the connector and the tool; the side panel does not show the question.
- OAuth: credentials saved before the upgrade have no `issuer` stamp; the SDK accepts them and stamps them on use, so no new login is needed (tested). Client ID Metadata Documents: a client opts in with `clientMetadataUrl` on its provider, an https URL serving its metadata document, used when the authorization server advertises `client_id_metadata_document_supported`. sitegeist would have to host that document (for example on the website); still a later item, dynamic registration keeps working.
- SSE: `SSEClientTransport` still ships in the v2 client. The fallback stays and connects with the 2025 handshake only, without a probe.

## Why

Nothing is broken today. `@modelcontextprotocol/sdk` 1.32.1 speaks protocol versions up to `2025-11-25`, and every current harness still accepts that. The reasons to move:

- The new protocol ships only in the SDK's v2 packages. The 1.x line gets bug and security fixes for a limited time (the SDK says at least six months after v2 shipped) and never gets `2026-07-28`.
- Three things sitegeist relies on are on the way out: server-initiated elicitation (removed from the 2026 protocol), the HTTP+SSE transport (deprecated) and dynamic client registration (deprecated). The spec's deprecation window is at least twelve months.
- Connectors that already speak `2026-07-28` can return `input_required` results and cacheable tool lists, which the extension cannot use yet.

## What changes in the protocol

Only the parts that touch the files above.

- **No handshake.** `initialize` and `notifications/initialized` are gone. Each request carries the protocol version, client info and client capabilities in `_meta` (`io.modelcontextprotocol/protocolVersion`, `.../clientInfo`, `.../clientCapabilities`). An optional `server/discover` call returns capabilities up front.
- **No server-to-client requests.** `elicitation/create`, `sampling/createMessage` and `roots/list` cannot be pushed. A tool that needs input returns `resultType: "input_required"`; the client answers by retrying the call with `inputResponses`.
- **HTTP headers.** Streamable HTTP requests must carry `Mcp-Method`, and `Mcp-Name` when they name a tool, plus `MCP-Protocol-Version`.
- **Cacheable lists.** `tools/list` results carry `ttlMs` and `cacheScope` and come back in a fixed order.
- **OAuth.** Clients must validate the `iss` parameter of the authorization response (RFC 9207), send `application_type` when they register, and keep credentials bound to the issuer that minted them. Dynamic client registration is deprecated in favor of Client ID Metadata Documents.

## What changes in the SDK

- The packages are `@modelcontextprotocol/server` and `@modelcontextprotocol/client` (2.4.0 on npm on 2026-11-24), plus `core`, `node`, `server-legacy` and `codemod`. They need Node 20 or later and `zod ^4.2.0`.
- Server: `McpServer` comes from `@modelcontextprotocol/server`. For the 2026 protocol, `server.connect(new StdioServerTransport())` is replaced by `serveStdio(() => buildServer())` from `@modelcontextprotocol/server/stdio`. A server connected the old way serves only 2025-era protocol. `serveStdio` keeps serving 2025 clients unless told `{ legacy: 'reject' }`.
- Server input: inside a tool handler, return `inputRequired({ inputRequests: { id: inputRequired.elicit({...}) } })` and read the answer on re-entry with `acceptedContent(ctx.mcpReq.inputResponses, 'id', schema)`. On a 2026 request the push APIs (`elicitInput`, `createMessage`, `listRoots`) fail with a local error before anything is sent. On a 2025 request they still work.
- Client: `new Client(info, { versionNegotiation: { mode: 'auto' } })` probes for the new protocol and falls back to `initialize`. The default mode is `'legacy'`. `client.getProtocolEra()` says which was chosen. The client sends the headers and `_meta` itself, caches list results on 2026 connections, and by default fulfils `input_required` through handlers registered with `setRequestHandler('elicitation/create', ...)`.
- Client OAuth: `transport.finishAuth(params)` takes the callback's `URLSearchParams` and checks `iss`; a mismatch throws `IssuerMismatchError`. The SDK stamps `issuer` on what it passes to `saveTokens` and `saveClientInformation` and passes `{ issuer }` to the getters. `application_type` is derived from the redirect URI, so a loopback redirect becomes `native`. New optional provider methods: `discoveryState` and `saveDiscoveryState`. `invalidateCredentials` is now called with `'client'` and `'tokens'` separately. The SDK still does not check `state`; the app must.
- The SDK repository ships a codemod (`@modelcontextprotocol/codemod`) and an upgrade skill under `skills/mcp-typescript-sdk-upgrade-to-v2/`. Read both before editing by hand.

### 2. CLI server: the host permission prompt

- Symptom on a 2026 connection: `server.server.elicitInput` (`cli/src/mcp.ts:166`) fails locally, the `catch` at 185 denies, and the user is never asked.
- How it works today: the extension sends a `permission_request` event (`src/bridge/native.ts:167`) while a tool call such as `navigate` is waiting, and `handlePermission` (157 to 193) asks through elicitation, then answers with `permission.respond`.
- Change: on a 2026 request the question has to come back as the tool's own result. The handler whose bridge call triggered the request returns `inputRequired` with the same three choices, and on re-entry sends `permission.respond` and finishes the call. Carry the bridge's `requestId` in `requestState`, not in process memory. Keep the `elicitInput` path for 2025 requests, and keep `SITEGEIST_AUTO_ALLOW=1` and the headless deny message working in both.
- Decide and write down: what happens to the pending bridge call between the two rounds. The extension times the request out after `PERMISSION_TIMEOUT_MS`.
- Check: an e2e case in "ask" mode for each era: the prompt appears, each of the three answers has its effect, and a client with no elicitation support gets the deny text.
